## What changed in this round

### Revision §22 — Driver service-area registration removed

- **Migration** `database/migrations/1791676800000_create-driver-onboarding.sql` amended in place (the draft was only ever exercised on
  disposable test databases; no persistent deployment was discovered): it now creates/drops **only `app.drivers`** with its own constraints
  (`drivers_pkey`, `drivers_user_uq`, `drivers_user_fk`, name/plate/type/status/version/time-order checks, and
  `drivers_not_active_not_accepting_ck`). No `driver_service_areas`, no `driver_service_areas_area_idx`. It references only `app.users`.
  No previously merged M00/Auth/Shop migration was touched. Scope of the amendment: removal of the second table, its FKs, index, and the
  now-false header/down comments.
- **M03** `DriverRepository`: `insertServiceAreas` removed; only `lockByUserId` and `insertPending` remain. `DriverModule` doc updated.
- **Coordinator** `DriverOnboardingService`: no `ServiceAreaRepository`, no area lock, no area insert. Logical request is exactly
  `{ full_name, plate_number }`. Lock order is M00 idempotency lock → user `FOR UPDATE` → existing Driver (`FOR UPDATE`) → Driver insert →
  DRIVER role grant → audit → outbox → idempotency result.
- **Parser** `parseDriverOnboardingBody`: required `full_name`, optional/null `plate_number`; every other key — including the legacy
  `service_area_ids` — is a generic `400 BAD_REQUEST` with no effects. `DRIVER_SERVICE_AREAS_MAX` and the 50-area cap are gone.
- No GPS field, province check, default area or location provider was added. Shop/service-area code (M02) is untouched.
- `INVALID_SERVICE_AREA` stays in the registry because Shop uses it.

### F1 — active guard no longer falls through

`DriverActiveGuard.requireDriverActive` had an exhaustive `switch` with no `default`: a status outside the union made the promise resolve
to `undefined`. It now has a `default` branch that throws `TechnicalError('internal', 'Unexpected driver status')` (safe, no row data).
The unit regression asserts on the promise itself (`await expect(pending).rejects.toBeInstanceOf(TechnicalError)`), never by reading
`driverId` after resolution.

*Regression proof on CI:* commit `3436a90` contains the new tests with the old guard — run 37725860160 fails with exactly
`DriverActiveGuard.requireDriverActive (A03-30) a status the guard does not know makes the guard promise itself reject with a safe
internal error, never resolve` and `… a row with no status at all also rejects instead of resolving` (`Received promise resolved instead of
rejected / Resolved to value: undefined`). Commit `ec60490` changes only `driver-active-guard.ts` and run 37725962020 passes them.

### F2 — PostgreSQL-backed guard tests

New `tests/integration/driver-active-guard.int.spec.ts`: the real `DriverActiveGuard` called inside a real M00 transaction
(`TransactionManager.withTransaction` over the real pool → real `TransactionContext`), against real `app.drivers` rows. No faked query
result and no HTTP endpoint. Cases: ACTIVE returns that user's own `driver_id` (and not another user's); PENDING →
`DRIVER_PENDING_APPROVAL`; SUSPENDED, CLOSING, CLOSED and a missing profile → `ROLE_NOT_AVAILABLE`; the answer follows a status change
(PENDING → ACTIVE → SUSPENDED) at call time; the guard is a pure read (row unchanged).

## Design decisions kept for the audit

1. Guard for SUSPENDED / CLOSING / CLOSED / missing → existing `ROLE_NOT_AVAILABLE` (accepted in §22); an unexpected status is a
   `TechnicalError('internal')`. The guard is a read participant on the caller's `TransactionContext`, takes no lock and is wired to no endpoint.
2. `onboarding_required` is true only for a user with no usable role, Shop not COMPLETED and Driver NOT_STARTED; a Driver profile of any
   status (CLOSED included) never routes back to creation.
3. No database constraint can require "a Driver has an area" any more, because the concept no longer exists.
