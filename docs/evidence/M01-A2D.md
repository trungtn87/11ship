## What was built

  and `driver_service_areas_area_idx`. No IF [NOT] EXISTS, no CASCADE; the down drops the two tables in dependency order. Applied
  migrations and M00 primitives were not touched.
- `POST /v1/onboarding/driver` (Bearer + Idempotency-Key). Always EXTERNAL / PENDING / `accepting_deliveries=false` / version 1.
  Body `full_name`, `plate_number` (optional), `service_area_ids`; every other field is rejected.
- M03 read port `DriverEligibilityReader` and `DriverActiveGuard.requireDriverActive(context, userId)`.
- Auth: one eligibility rule for login, `/auth/me` and `role/select` (see below); `/auth/me` gains `onboarding.driver`.
- New error codes `DRIVER_PROFILE_EXISTS` (409) and `DRIVER_PENDING_APPROVAL` (403) — 28 codes in total.
- Outbox `driver.onboarded.v1` with payload exactly `{driver_id, user_id}`.

## Module wiring

`DriverModule` imports nothing. `AuthModule` imports it for the read port only; `OnboardingModule` imports it for the repository.
`AuthModule.register(...)` is still built once and passed to `OnboardingModule.register(auth)`. No `forwardRef`, no direct SQL on M03
tables from Auth (asserted by `driver-boundary.spec.ts`).

## Lock order (inside the executor callback)

idempotency record (M00) → user row FOR UPDATE → existing Driver (`FOR UPDATE`) → service areas FOR SHARE in UUID order (ids are
sorted before locking, so two requests can never lock in opposite orders) → Driver insert → areas → DRIVER role → audit → outbox →
idempotency completion. Areas must exist and be ACTIVE *after* the lock. A replay re-checks the user (`authorize` hook).

## Design decisions and open items to review

1. **Active guard for non-ACTIVE, non-PENDING states.** The contract names `DRIVER_PENDING_APPROVAL` for PENDING only. For
   SUSPENDED / CLOSING / CLOSED / no profile the guard fails closed with the existing `ROLE_NOT_AVAILABLE` and says so in code. No new
   semantics were added; the Owner should decide whether those states need their own codes. The guard is not wired to any endpoint.
2. **`onboarding_required`.** It is true only when the user has no usable role and Shop is not COMPLETED and Driver is NOT_STARTED. A user
   with a Driver profile of any status (including CLOSED) is never sent back to onboarding; a CLOSED profile that cannot be selected
   would otherwise be a dead end. Shop DISABLED keeps its A2S semantics.
3. **`DRIVER_SERVICE_AREAS_MAX = 50`** is my cap against pathological bodies (not in the brief). Owner to confirm or change.
4. **Malformed UUID → 400 BAD_REQUEST; duplicate id → `INVALID_SERVICE_AREA`; well-formed but unknown / inactive → `INVALID_SERVICE_AREA`.**
   Upper-case UUIDs are malformed (canonical lower-case only, as elsewhere in the repo).
5. **No database constraint for "at least one area".** A CHECK cannot span tables; the service writes the Driver and its areas in one
   transaction and the validator requires ≥ 1 (a DB-level guarantee would need a deferred constraint trigger, left for the Owner).
6. **Extra index** `driver_service_areas_area_idx` serves the FK from the area side (area row locks and "who covers this area").
7. The table CHECK allows the whole status vocabulary and PLATFORM, but A2D inserts only the one shape; nothing in A2D can change them.
