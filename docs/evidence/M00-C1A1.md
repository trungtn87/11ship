## Contract triển khai

### Exact-key protocol

Identity là `(scope_type, scope_id, operation_id, idempotency_key)`. `Idempotency-Key` bắt buộc UUID dạng canonical, normalize hex lowercase, nil UUID bị từ chối.

Executor sở hữu outer transaction:

1. đặt `lock_timeout` bằng advisory budget;
2. lấy `pg_advisory_xact_lock(int32,int32)` từ primitive A0;
3. chỉ SQLSTATE 55P03 ngay tại advisory acquisition được map thành `IDEMPOTENCY_BUSY`;
4. restore `lock_timeout` về business-row-lock budget;
5. select exact record bằng `FOR UPDATE`;
6. dùng `clock_timestamp()`/epoch milliseconds từ PostgreSQL cho expiry decision;
7. existing record dùng **historical crypto key của record** để fingerprint/decrypt;
8. new owner chạy callback một lần, chỉ 2xx được encrypt + insert completed record trong cùng transaction.

Row-lock timeout, query timeout và database outage không bị đổi nhầm thành BUSY.

### Fingerprint / replay / key rotation

- Logical request được canonicalize + HMAC-SHA-256 bằng key version của record.
- Request plaintext/password/proof token không được persist.
- Replay payload được bounded JSON validation rồi AES-256-GCM bằng primitive A0; DB chỉ giữ ciphertext/IV/tag.
- AAD bind format version, record identity, request fingerprint, replay guard, status và replay expiry.
- Timestamp AAD/persist được tạo từ **integer epoch milliseconds**, column là `timestamptz(3)`.
- Active key rotation không làm mất khả năng nhận fingerprint/decrypt record cũ nếu historical key còn trong keyring.
- Historical key thiếu trong dedupe window → `IDEMPOTENCY_KEY_UNAVAILABLE`, callback không chạy lại.
- Tamper ciphertext/tag/IV/guard/status/replay expiry → fail closed.

### Sensitive replay authorization

Executor hỗ trợ server-owned replay authorization hook trước decrypt. Integration fixture C18/C19 dùng test-only tables cho proof/user/session; không có Auth schema migration.

Guard bind `proof_id + user_id + session_id`. Authorization fixture lock theo thứ tự **proof → user → session**, rồi đọc mutable state ở query riêng **sau khi row lock đã được cấp**. Vì vậy revoke/disable/binding/session-expiry được quyết định bằng fresh committed state; test còn giữ row lock trước để chứng minh updater concurrent phải chờ.

Proof đã consume hoặc naturally expired vẫn có thể resolve/replay record đã committed; chỉ new-owner callback enforce proof unused/fresh. Explicit invalidation deny replay. Changed logical request cùng key bị conflict trước khi mint token mới.

### TTL / cleanup

Config server-owned:

- advisory wait default 250ms, 1..5000ms và phải < statement timeout;
- business lock timeout default 500ms và phải < statement timeout;
- replay TTL default 900s;
- dedupe TTL default 604800s;
- `1 <= replay <= dedupe <= 604800`.

Operation override chỉ qua immutable `IdempotencyOperationRegistry` trong server code; request không có TTL field.

Equality là expired. Nếu replay hết hạn nhưng dedupe còn: giữ tombstone và trả `IDEMPOTENCY_REPLAY_EXPIRED`, không rerun. Nếu dedupe đã hết mà cleanup chưa chạy: executor xóa exact row dưới lock rồi mở window mới; business invariant vẫn phải recheck.

Cleanup primitive chạy bounded batch, `FOR UPDATE SKIP LOCKED`, không lấy advisory lock sau row lock:

1. phase replay-expired: NULL ciphertext/IV/tag, giữ tombstone;
2. phase dedupe-expired: xóa record.

A1 **không** thêm production scheduler; C1B/C cũng chưa được mở.

## Concurrency / fault-injection disclosure

Các concurrency assertions chính dùng PostgreSQL thật, independent connections và deterministic barriers. Không dùng `Promise.all` đơn thuần làm bằng chứng overlap.

- Advisory wait và row-lock wait được quan sát bằng PostgreSQL lock state.
- Revoke updater được chứng minh đang chờ row lock do replay giữ.
- Cleanup `SKIP LOCKED` được kiểm bằng cách giữ thật một idempotency row lock.
- Hash-collision test inject lock-key function cố định để ép hai exact key khác nhau cùng advisory pair; exact-row lookup vẫn không cross-replay.
- COMMIT-unknown là fault inject duy nhất ở client boundary: server thật đã COMMIT, acknowledgement bị giả lập mất; retry qua pool bình thường replay record committed.
- Tamper tests cố ý mutate DB record sau commit để kiểm fail-closed.

## Privacy / secrets

Integration dùng marker password, verification token và access token:

- logical request password/proof token không xuất hiện trong serialized `idempotency_records`;
- access token replay chỉ tồn tại plaintext trong memory; DB row chứa ciphertext, không marker plaintext;
- replay guard dùng non-secret identifiers và shared 4KiB safe-JSON policy;
- A1 không thêm logging path chứa logical request/ciphertext/plaintext; A0 error/logger regression vẫn pass;
- config failure chỉ in **tên biến**, không in keyring/database secret.
