## What was built

- Schema (M02): `app.service_areas`, `app.shops`, `app.shop_members`; OWNER invariants as partial unique indexes; no seed, no trigger, no CASCADE, no IF [NOT] EXISTS.
- `PUT /v1/onboarding/shop/profile` (201 create / 200 update) and `POST /v1/onboarding/shop/complete` (200), both behind `SessionAuthGuard`, executed through the M00 `IdempotencyExecutor` (scope `user`, scope id = authenticated user id, operations `onboarding.shop.profile.save.v1` / `onboarding.shop.complete.v1`).
- Completion: shop ACTIVE, `accepting_orders=false`, version + 1, SHOP role granted through the narrow `RoleGrantParticipant`, audit `onboarding.shop.complete.v1`, outbox `shop.onboarded.v1` with payload exactly `{"shop_id","user_id"}`. No role auto-select, no new token.
- Auth integration: read-only `ShopEligibilityReader` (M02) used by `/auth/me`, login and `role/select`; `/auth/me` gains `onboarding: {shop: NOT_STARTED|INCOMPLETE|COMPLETED, driver: "NOT_STARTED"}` (driver is a constant; no driver table is read). SHOP is listed and selectable only with the SHOP role AND an OWNER membership of an ACTIVE shop; a stray SHOP role gives `ROLE_NOT_AVAILABLE`.
- New errors: `SHOP_ONBOARDING_EXISTS` 409, `SHOP_PROFILE_INCOMPLETE` 409, `INVALID_SERVICE_AREA` 400, `VERSION_CONFLICT` 409.

## Module wiring

`ShopModule` (imports nothing; exports `ServiceAreaRepository`, `ShopRepository`, `ShopEligibilityReader`) ← `AuthModule` (imports ShopModule for the read port only; exports `SessionAuthGuard`, `SessionService`, `RoleGrantParticipant`) ← `OnboardingModule.register(auth)`. `AppModule` builds `AuthModule.register(...)` once and passes the same object to Onboarding. No `forwardRef` anywhere (asserted by `shop-boundary.spec.ts`).

## Lock order (inside the executor callback)

M00 advisory + record lock → user row `FOR UPDATE` → OWNER membership `FOR UPDATE` → shop `FOR UPDATE` → service area `FOR SHARE` → shop/membership/role writes → audit → outbox → idempotency record. `FOR SHARE` on the area blocks an operator `UPDATE` while still letting any number of shops share the same area.

## Concurrency (deterministic barriers, no sleeps; every overlap observed in `pg_locks` before release)

1. Two creates, different keys, user row held by a test transaction → one 201, one `SHOP_ONBOARDING_EXISTS`, one shop, one membership, one audit row.
2. Two completions, different keys → one 200, one `SHOP_ONBOARDING_EXISTS`, one role grant, one event, one audit row.
3. Same key sent twice → one effect (second is a replay or `IDEMPOTENCY_BUSY`).
4. Area deactivated before completion reads it (uncommitted operator UPDATE) → completion waits, then `INVALID_SERVICE_AREA`, nothing written. Same for profile save.
5. Area deactivation after completion took `FOR SHARE` (stall trigger on the ACTIVE transition) → operator UPDATE blocks until the completion commits; final shop ACTIVE, area INACTIVE.
6. A popular area does not serialize shops: two completions finish while a third transaction holds `FOR SHARE`.

## Fault matrix (`shop-onboarding-faults.int.spec.ts`; trigger raises XX001 for one test user's rows only)

- Save: shop insert, membership insert, audit insert, idempotency record insert.
- Complete: shop ACTIVE update, SHOP role insert, audit insert, outbox insert, idempotency record insert.
- Every case: 5xx without leaking the injected message or contact data; no shop/membership/role/audit/outbox/record left; draft unchanged; the same Idempotency-Key then succeeds.

## Design decisions to review

- Login and `/me` filter SHOP out of `available_roles` unless the shop is ACTIVE (response shape of login unchanged).
- A DISABLED shop projects as `COMPLETED` but is not selectable.
- `expected_version` with no draft → `VERSION_CONFLICT`; save or complete against an ACTIVE/DISABLED shop → `SHOP_ONBOARDING_EXISTS`; complete with no shop → `SHOP_PROFILE_INCOMPLETE`.
- Idempotent replay is "sensitive": it re-locks the user and refuses once the account is not ACTIVE.
- A1 test adjustments: `grantRole(..., 'SHOP')` fixture now also creates an ACTIVE owned shop (`grantStrayRole` gives the bare role); exact `/me` shape gained `onboarding`; auth-migration spec treats the Shop migration as the new last one; error registry counts 22 → 26.
- Commits `cd83b83`, `10c53eb`, `709d24a`, `2a6da2b` have the attribution trailers in the subject paragraph (no blank line before them); history was not rewritten after push.

### F2 — `/auth/me` is one coherent snapshot

- `UserRepository.lockByIdForShare` (Auth): `SELECT ... FROM app.users WHERE user_id = $1::uuid FOR SHARE`.
- `RoleContextService.me`: shared user lock → re-check user exists and is ACTIVE (`SESSION_INVALID` / `ACCOUNT_DISABLED`) → roles → Shop eligibility, in one transaction. Completion still takes the user `FOR UPDATE`, so the two serialize at the user root. No SERIALIZABLE, no Auth SQL against M02 tables, no `forwardRef`, mutation lock order untouched.

Deterministic race proof — `shop-onboarding-concurrency.int.spec.ts` → "/auth/me is one coherent snapshot against a concurrent completion":

1. A draft exists; `/auth/me` reports `INCOMPLETE`, no roles, `onboarding_required = true`.
2. A completion is stalled by the existing test-only trigger on the ACTIVE transition, behind an advisory lock the test holds. Observed in `pg_locks` (advisory waiter). At this point it holds the user row `FOR UPDATE`, has not granted the role and has not committed; `user_roles` is still empty for the user.
3. `/auth/me` is started. The test then observes, in `pg_locks` joined to `pg_stat_activity`, exactly one backend with an ungranted `transactionid`/`tuple` lock, `wait_event_type = 'Lock'`, whose running statement is the `FOR SHARE` on `app.users`. No sleep decides this; the wait is a server fact. The `/auth/me` promise is still unsettled and the completion is still stalled.
4. The gate is released. Completion → 200. `/auth/me` → 200 with `available_roles = ["SHOP"]`, `onboarding.shop = "COMPLETED"`, `onboarding_required = false`, `role_selection_required = true`, `active_role = null`. No waiter remains.

The same sequence was also run by hand against a local PostgreSQL 16 with `psql` (holder `FOR UPDATE`, reader `FOR SHARE` through the extended protocol): the observation query returned 0 before the reader, 1 while it waited, 0 after; the reader got its lock within a millisecond of the holder's commit and read the SHOP role and the ACTIVE shop.

Companions in the same describe: "the shared lock does not serialize readers" (two `/auth/me` answer while a third transaction holds the user `FOR SHARE`) and "/auth/me writes nothing and leaves the A1 session as it was". Unit: `role-context-service.spec.ts` (order `user.share → roles → shop` in one transaction; re-check after the lock; the repository statement is a real `FOR SHARE`; the single `FOR UPDATE` of mutations is unchanged).

Operational note: `/auth/me` now waits for a completion or role selection of the same user that is in flight. That wait is bounded by the existing statement timeout, like every other statement.

### F3 — `onboarding_required` for a completed but unselectable Shop

One rule next to `availableRoles()`: `roleContext(held, shop, activeRole)` in `auth/available-roles.ts`, used by login, `/auth/me` and the role-select response.

- `onboarding_required = no selectable role AND onboarding.shop is NOT_STARTED or INCOMPLETE`
- `role_selection_required = at least one selectable role AND active_role is null`

| State | `available_roles` | `onboarding.shop` | `onboarding_required` | `role_selection_required` (no active role) |
| --- | --- | --- | --- | --- |
| NOT_STARTED (also with a stray SHOP role) | `[]` | `NOT_STARTED` | true | false |
| INCOMPLETE (also with a stray SHOP role) | `[]` | `INCOMPLETE` | true | false |
| ACTIVE | `["SHOP"]` | `COMPLETED` | false | true |
| DISABLED, Shop-only | `[]` | `COMPLETED` | false | false |
| DRIVER + DISABLED Shop | `["DRIVER"]` | `COMPLETED` | false | true |

SHOP select on a DISABLED shop stays `ROLE_NOT_AVAILABLE`. DRIVER behavior is unchanged.

Tests: unit `available-roles.spec.ts` (the matrix, and that login and `/me` compute neither flag themselves), `role-context-service.spec.ts` and `login-service.spec.ts` (the same matrix through each service); integration `shop-onboarding.int.spec.ts` → "onboarding_required / role_selection_required at /me and at login" — NOT_STARTED and INCOMPLETE (with and without a stray role), ACTIVE, DISABLED Shop-only (also shows save and complete both answer `SHOP_ONBOARDING_EXISTS`, which is why onboarding must not be requested), DRIVER + DISABLED (DRIVER selectable, flags after selection), DRIVER with no shop. Each case asserts `/me` and a fresh login agree.
