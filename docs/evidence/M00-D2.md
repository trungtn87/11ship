## 2. What changed

**Schema** (new migration `1791849600000_add-users-account-origin.sql`, no applied migration edited):
`app.users.account_origin varchar(24) NOT NULL DEFAULT 'PHONE_VERIFIED'`; `phone_verified_at` becomes nullable;
`users_account_origin_ck` (two values) and `users_origin_verified_ck` (PHONE_VERIFIED ⇔ proof time present, STAGING_FIXTURE ⇔
absent). Existing rows backfill as PHONE_VERIFIED (correct: the column was NOT NULL before). Down refuses while a fixture exists.

**Config** (`staging-fixtures-config.ts`, `app-config.ts`): `AUTH_STAGING_FIXTURES_ENABLED` (exactly `true`/`false`; `true` only for
`APP_ENV=staging`), `AUTH_STAGING_ALLOWED_PHONES` (JSON array, 1–20, unique, normalized +84; required when on, an error when
present while off). Errors name only the variable. The allowlist object is redacted for logging/inspection.

**Policy** (`auth/account-origin.ts`): one object decides for both origins. PHONE_VERIFIED is accepted only when fixture mode is
off; STAGING_FIXTURE only when fixture mode is on **and** the phone is in the allowlist. `createAccountOriginPolicy` enables the
mode only for `appEnv === 'staging'` (a second barrier besides startup validation). Applied at: login (after the password is
verified, denial is `INVALID_CREDENTIALS`), bearer authentication (`SESSION_INVALID`), and again inside `SessionAuthorizationParticipant`
under the user→session row locks for every authorized command and `/auth/me`. The origin always comes from the database row.
Without an explicit binding the standard policy applies (fail closed).

**OTP / register**: `DisabledOtpProvider` is bound on staging only with the mode on (production is still refused, as before).
`requestOtp`, `verifyOtp` and `register` answer `503 AUTH_REGISTRATION_UNAVAILABLE` before any database access, hash, idempotency
call or provider call. There is no public fake OTP.

**Seed command** (`npm run staging:seed-fixtures`, `scripts/staging-seed-fixtures.js`, `auth/staging-fixture-seeder.ts`): same target
gates as `db:migrate:remote` (shared `checkRemoteTargets`: session pooler :5432, same host/port/database/project, different roles,
typed target), strict TLS from the compiled application rules, operator credential = `MIGRATION_DATABASE_URL`, data only on stdin
(no arguments accepted), strict payload (`phone`, `password` only). One transaction, one fixed advisory lock; hashing before the
transaction; an existing fixture is skipped untouched; a PHONE_VERIFIED phone aborts and rolls back the whole batch; audit
`auth.staging_fixture_created.v1` (actor `OPERATOR`/`staging-seed-cli`) in the same transaction; no role, profile, session, OTP/proof
record or outbox event. Output is counts and safe codes.

**API**: login response and `GET /v1/auth/me` gain `phone_verification_status` (`VERIFIED` | `UNVERIFIED_TEST`). New error code
`AUTH_REGISTRATION_UNAVAILABLE` (HTTP 503). No new endpoint.

**Dashboard**: `docs/progress/plan.yml` leaf `M00-D2` now has `design_pr: 26`, `acceptance: docs/tasks/M00-D2-staging-fixtures.md`,
`evidence: docs/evidence/M00-D2.md`, `requires_main_ci_green: true`. `tests/progress/m00-d-plan.test.mjs` covers: design PR open →
design review, merged design + draft PR → CLAUDE_CODING, merged green PR → DONE, failed required check → not DONE, red main →
BLOCKED_BY_CI.

## 4. Decisions and limits

- **Fixture mode is exclusive.** While on, registered (PHONE_VERIFIED) accounts are not accepted either, and registration is closed;
  otherwise a live OTP-less staging could not be told apart from a half-open one. Switching the mode off on staging without an SMS
  provider means the service refuses to start (by design, fail closed).
- **Policy rejection is not revocation.** A rejected old session stays valid in the database; allowing the phone again restores it.
- `render.yaml` is unchanged: the two variables are set in the Render dashboard (the allowlist is a secret). Runbook §8 documents it.
- Not verified here (cannot be from this environment): any run against the real Supabase pooler/Render; the seed under the operator
  role through Supavisor; local PostgreSQL 17 integration runs (this workspace has none; CI provides it); real Argon2 timing on Render
  Free.
- Not done on purpose: UI, ADMIN/SYSTEM, wallet, delivery, real SMS, deploy, remote migration, remote seed, marking Ready, merging.

## 5. Contract for the HTML UI (not implemented)

- `POST /v1/auth/login` → `data.phone_verification_status`; `GET /v1/auth/me` → `data.phone_verification_status`. `UNVERIFIED_TEST` is a
  display hint ("test account, phone not verified"), never an authorization source.
- While fixture mode is on, the OTP request/verify and register endpoints answer `503 AUTH_REGISTRATION_UNAVAILABLE`: hide those screens.
- Login failure stays `INVALID_CREDENTIALS`; a session the process no longer accepts answers `SESSION_INVALID` → return to login.
- A fixture has no role and no profile after login: continue through the existing SHOP / DRIVER onboarding endpoints.
